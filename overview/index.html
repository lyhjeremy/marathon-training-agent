An agent loop with a code-based critic, rebuilt on structured outputs in November 2026

A training-plan agent that checks its own plan before you see it

November 2026: with the plan written into a JSON schema and checked in code, 6 of 6 plans passed every safety check and none came back the wrong length. The original loop, on the same model and six frozen runners, passed 1 of 6 and returned 3 plans longer than the runner had weeks. The structured version costs a median $0.10 and 47 seconds a plan against $0.22 and 114 seconds.

Before that, run on its own three-runner safety panel (five plans), the critique and revise loop moved the share of plans passing all four safety checks from 1 in 5 to 2 in 5, and one of those two came back 18 weeks long for a runner with 10. Each plan cost $1.19 at API prices and took 172 seconds. In the recorded run below, asked for a 3:05 Boston off 22 miles a week, it recommended 3:20 and its critic caught five problems in the first draft. The agent is a LangGraph state machine with five nodes. It judges whether the goal is realistic, drafts a periodized week-by-week plan, and tailors it to the race and the forecast heat. Then deterministic safety checks in Python run alongside an LLM review, and a revise node fixes whatever they flag and loops back, up to a revision budget.

November 2026: structured outputs

Six runners, six plans that pass, none the wrong length

With the plan in a schema and validated in code, 6 of 6 plans passed every check and none came back the wrong length. The original loop, on the same model and the same six frozen runners, passed 1 of 6, and 3 of 6 came back longer than the runner had weeks: 17 weeks for a 12-week runner, 18 for 10, 15 for 8. The structured agent made 1.8 model calls a plan against 7.7, cost a median $0.10 against $0.22 (API-equivalent, as the Claude CLI reports it) and took a median 47 s against 114 s, p95 66 s against 129 s. Both ran on claude-sonnet-5-5 with the same isolated CLI flags, one plan at a time on an Apple M4. The six runners, the three from November 5 with a recent half-marathon time added and three new ones, were frozen at commit d397cd5 before either system saw them. Six runners is a small set; it shows the failure modes went away on these, not a rate.

The fix moves the parts that kept going wrong into code. src/schema.py defines the plan as pydantic models: every week has exactly seven sessions, each with a day, a type from a fixed list (rest, easy, long, tempo, intervals, marathon pace, hills, race) and a distance. A validator then checks what a schema cannot: the plan has exactly as many weeks as the runner has, the weeks run 1 to N, each day appears once, running days do not exceed the runner's days per week, phases go Base, Build, Peak, Taper, and the last week holds the race. The assessment is a calculation: Riegel's formula from the runner's recent half marathon, and a peak mileage from the 10% rule the old plan prompt already stated. src/structured.py is the new LangGraph loop: assess in code, one draft in the schema, validate in code, and up to two repairs that quote every validation error back to the model. The old LLM review is gone; the four safety checks are unchanged and score both versions.

Where each version failed

  1. The original loop, runner r2 (New York, 10 weeks). The draft had 10 weeks. Critique listed 15 issues, three from the code and twelve from the LLM reviewer, among them Only 10 weeks total ... too short and too compressed a build. Revision 1 answered that by lengthening the plan; after revision 2 the plan had 18 weeks, the code checks passed, and the reviewer still listed 6 issues. The reviewer's own opinions pushed the plan away from the runner's input, and no check compared the length.
  2. The original loop, ramp jumps. r1, r3, r4 and r6 ended with weeks more than 20% above the week before, 1 to 3 per plan, after two revisions each. In its drafts the race week's 26.2 miles also counted as a long run over the 22.5-mile cap, since that schema had no way to mark the race.
  3. The structured agent, first drafts. Only 2 of 6 first drafts were valid. The other four broke a limit I set in the schema, a 120-character cap on a session note (weeks.11.sessions.6.note: String should have at most 120 characters), and each was fixed by one repair. On r2 the repair then added a ramp jump (27 to 33 miles in week 5), which the second repair removed. So 5 of the 11 structured calls were repairs, four of them caused by a limit that adds nothing to safety.

The same checks over MCP

src/mcp_server.py serves four tools over stdio with the same SDK as my strategy coach: assess_runner, plan_schema, validate_plan and safety_checks. None calls a model, so a client such as Claude Code can write a plan itself and have it checked by the agent's own code. tests/test_mcp.py starts the server, lists the tools and validates a plan through it on every push.

What I would do next

  • Raise or drop the note-length cap, which caused four of five repairs, and measure the first-draft valid rate again.
  • Run each runner three times through the structured agent, so the pass rate has a spread and not one run per runner.
  • Check the Riegel targets against real race pairs (a half and a marathon by the same runner); Riegel is known to be optimistic for low-mileage runners, which is most of this panel.
  • Add an 80/20 easy-to-hard check now that sessions have types, which the old weekly-total schema could not express.

Why a graph

A single prompt can't check its own arithmetic

Ask a language model for a sixteen-week marathon plan and the result looks right, even when it raises mileage 30% in a week, skips the taper or prescribes a 26-mile long run. A coach would spot those errors at a glance; in fluent prose they are easy to read past.

The graph adds a place to catch them. The critique node runs _safety_checks, which reads the plan's numbers and returns a list of problems, and merges that with issues an LLM reviewer raises. _route sends the plan to revise when there are issues and revisions remain (two by default), and ends the run otherwise.

assess
Judges whether the goal is realistic for the runner's mileage, longest run and weeks to go; returns a recommended goal time and a peak weekly mileage as JSON.
plan
Drafts the Base, Build, Peak and Taper weeks in a fixed JSON schema: miles, long run, quality sessions, focus.
adjust
Rewrites workout emphasis for the race using src/knowledge.py: a simulated course penalty against Berlin, about 1 minute per °F above 55°F, and the 30 km wall.
critique
Deterministic checks plus an LLM review; the plan passes only with zero issues.
revise
Fixes the listed issues and returns the full plan to critique.

Interfaces

CLI and a Streamlit app

python -m src.cli takes flags or prompts for them and prints the assessment, the plan table and the trace. streamlit run app.py wraps the same graph: set the race in the sidebar and watch the run stream through the nodes, then read the plan table, a weekly-mileage chart, the safety verdict and the trace. Generation uses the Claude CLI by default or the Anthropic API with ANTHROPIC_API_KEY; CLAUDE_MODEL can pick a faster model for the several calls a run makes. There is no hosted demo.

Limitations

Five plans, and the loop barely helps

The measured panel is five plans from three synthetic runners, so 1 in 5 against 2 in 5 is not a stable rate, but the failures in it are real: revisions that leave a flagged jump in place, add new ones, or change the plan's length. The recorded run in which the critic caught five issues and fixed them in one revision is the good case, not the typical one.

The deterministic checks cover four rules. Anything else, such as too many hard days or a monotonous build, depends on the LLM reviewer. The plan is generated advice for an adult runner and is no substitute for coaching or medical guidance.

The course figures in src/knowledge.py are simulated. They come from an earlier version of my Majors course-difficulty simulation, which ran on a simulated field with course penalties planted in code, so they are not measurements of the courses, and they differ from the current study: the file has London at 28 s and Tokyo at 33 s against Berlin and a Boston index of 1.036, where the study's paired method gives 30.7 s, 21.0 s and a composite of 1.0092. The file says so in a comment, and the course line it passes to the adjust prompt now calls the figure a simulated estimate, not a race result. They only steer the wording of adjust, and none of the safety checks reads them.

The November comparison is one run per runner on six synthetic runners I wrote, so 6 of 6 against 1 of 6 shows the failure modes, not a stable rate. It drops the LLM reviewer, so the structured plans are judged only by the four safety checks and the validator; the reviewer's points about long-run share, for example, are no longer checked by anything. The Riegel target and the 10% peak rule are standard rules of thumb, not fitted to these runners.
